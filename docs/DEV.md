# Wadhu developer notes

Commands and paths below are from the **workspace root** (the parent of
`docs/`). Doctrine (what goes where, independence rules) is in
[`WADHU_VISION_AND_PRINCIPLES.md`](WADHU_VISION_AND_PRINCIPLES.md); crate
rules are in [`CRATES.md`](CRATES.md). This file is the how-to.

## Workspace layout

```text
wadhu-workspace/
├── Cargo.toml              workspace: members, [workspace.package], [workspace.dependencies], [patch]
├── .cargo/config.toml      cargo aliases (<app>-dev), Windows cross linker, default window icons
├── apps/<app>/             independent apps (package wadhu-<app>); never depend on each other
├── crates/<crate>/         reusable, self-contained libraries (package wadhu-<crate>)
├── sites/wadhu/            Makepad 2 brand site → wadhu.com (Firebase)
├── tools/<app>-dev/        one thin `cargo <app>-dev` shim per app → apps/<app>/scripts/dev.sh
├── templates/              starters copied by scripts/new-app.sh / new-crate.sh (kept compiling)
│   ├── app/                Makepad 2 app (wadhu-template-app)
│   ├── crate/              plain-Rust library (wadhu-template-crate)
│   └── widgets/            Makepad 2 widget library + runnable demo (wadhu-template-widgets)
├── scripts/                tooling that names no app (setup, env, icons, scaffolding, checks)
├── patches/makepad/        Wadhu's patches on upstream Makepad 2 (ordered in setup-makepad.sh)
├── vendor/makepad/         generated by scripts/setup-makepad.sh — gitignored, never edit
├── assets/                 brand masters (images/) and default window icons (icons/)
└── docs/                   Wadhu-wide docs (this folder)
```

Each app follows the same internal shape (copied from `templates/app`):
`src/main.rs` (Makepad shell), `src/lib.rs` (non-UI, testable),
`src/identity.rs`, `build.rs`, `env/{development,production}.env`,
`scripts/`, `docs/`, optional `assets/` and `resources/`.

## First-time setup

```bash
# Rust stable (edition 2024). Tools used by scripts:
#   rsync, patch, jq, ImageMagick (magick); optional: Xvfb + xdotool (screenshots),
#   mingw-w64-gcc (Windows cross builds)
./scripts/setup-makepad.sh        # builds vendor/makepad (offline if cargo's git cache has the rev)
cargo build --workspace --all-targets
cargo test --workspace
./scripts/check-independence.sh
```

## Everyday commands

```bash
cargo template-app-dev                              # template app, live dev (--hot --remote)
cargo run -p wadhu-template-widgets --example demo  # widget crate demo
cargo test --workspace                              # unit + integration + doc tests
./scripts/check-independence.sh                     # §3 rules: no sibling coupling
```

`--hot` reloads `script_mod!` UI on save; `--remote` enables the tweaker
(**F12**) and tags the window title `[remote]`.

## Adding an app or a crate

```bash
./scripts/new-app.sh print-bridge --label "Print Bridge"   # id defaults to com.wadhu.printbridge
./scripts/new-crate.sh escpos                              # plain-Rust library
./scripts/new-crate.sh status-chips --widgets              # Makepad 2 widget library
```

Both copy a template (copy-then-diverge: nothing links back to it),
rename every identifier, register the workspace member (and for apps the
`tools/<app>-dev` shim and the `cargo <app>-dev` alias), then run the
independence check and build/tests. After creating an app, write its
brief (`apps/<app>/docs/<APP>.md`) and, once it ships, add it to
`default-members` in `Cargo.toml`.

An app uses a crate by path: `wadhu-escpos = { path = "../../crates/escpos" }`.
A Makepad widget crate is registered in the app's `AppMain::script_mod`,
after `makepad_widgets::script_mod(vm)` and before the app's own module,
and the app's `script_mod!` adds `use mod.widgets.*`.

## Env and app ids

Each app owns `env/development.env` and `env/production.env`:

```bash
WADHU_ENV=development
WADHU_APP_ID=com.wadhu.<app>.debug   # production: com.wadhu.<app>
WADHU_APP_LABEL="<Label> Dev"                # production: "<Label>"
```

- `build.rs` bakes the file chosen by `WADHU_ENV` (else Cargo `release` →
  production, otherwise development) into the binary; `src/identity.rs`
  reads it. Scripts load the same file with `scripts/load-wadhu-env.sh`.
- Development ids always end in `.debug`, so dev and prod installs never
  share a package, data dir or bundle (a test in `identity.rs` checks it).
- **Ids follow the brand domain, not the company name.** Wadhu’s domain is
  `wadhu.com`, so apps default to `com.wadhu.<app>` (dashes stripped). Same
  rule as other Gotigin brands (`tabiyat.shop` → `com.tabiyat`,
  `kirano.shop` → `com.kirano`). Gotigin is the company; it is **not** in
  the reverse-DNS id. If an app later owns its own domain, use that
  instead. Set the id once before the first release and never change it.
- Production Windows builds get the GUI subsystem (`wadhu_hide_console`
  cfg from `build.rs`); development keeps the console for logs.

## Icons

```bash
./scripts/generate-app-icons.sh assets/images/wadhu-brand-logo.png assets/icons   # workspace default
./apps/<app>/scripts/generate-icons.sh   # from apps/<app>/assets/app-icon.png → apps/<app>/resources/
```

`.cargo/config.toml` points `MAKEPAD_APP_ICON_*` at `assets/icons/` (the
Wadhu mark). An app's `dev.sh` exports its own icons once
`resources/icon_32.png` exists. Exported variables beat Cargo `[env]`.

## Makepad 2

- **Makepad 2 only**: `script_mod!`, `AppMain::script_mod`, `#[derive(Script, ScriptHook, Widget)]`.
  Never use Makepad 1 docs, examples or APIs (`live_design!`, `LiveHook`).
- `vendor/makepad` is **generated**: upstream commit `MAKEPAD_REV` (in
  `scripts/setup-makepad.sh`) plus every patch in `patches/makepad/`, in
  the order of the script's `PATCHES` list, plus
  `scripts/fix-makepad-rust-deprecations.sh`. It is gitignored. An edit
  made only in `vendor/` is lost on the next setup.
- The rev and patch set are **the same as the other Gotigin workspaces**
  (Kumkaj), so a Wadhu crate compiles the same here and inside a consumer.
  Change them deliberately in every workspace, and note it here.
- Patches apply with `--fuzz=0`: a hunk whose context no longer matches
  **fails** instead of landing in the wrong place. (On 2026-11-08 four
  patches inherited from Kumkaj were regenerated here: three needed fuzz,
  and `scroll_touch_orphan_unblock` had silently put Rust code into
  `scroll_bar.rs`'s script DSL, which raised script errors on every mouse
  event. `drag_scroll_touch_only` also had a hand-miscounted hunk header.)

### Changing a patch (never hand-edit hunks)

1. Build a scratch tree: upstream at `MAKEPAD_REV` plus the patches *before*
   the one you are changing (copy the loop from `setup-makepad.sh`).
2. Copy the touched files aside as "before", make the change, then
   `diff -u --label a/<path> --label b/<path> before after > patches/makepad/<name>.rs.patch`.
3. Run `./scripts/setup-makepad.sh`. Every later patch must still apply at
   fuzz 0; rebuild and look at the screen.

### Agent notes (verified on this rev)

- A plain `View { show_bg: true draw_bg +: {color: …} }` paints **nothing**
  here; use `SolidView { draw_bg +: {color: #x0d0b3a} }` (or `RoundedView`)
  for a solid background.
- Colours in script: `#xRRGGBB`; text: `draw_text.color`, `draw_text.text_style.font_size`.
- A library registers widgets as `mod.widgets.<Name>Base = #(<Name>::register_widget(vm))`
  plus `mod.widgets.<Name> = set_type_default() do mod.widgets.<Name>Base {…}`
  and exposes `pub fn script_mod(vm)`. Script names are global across
  crates, so prefix them with the crate's name (`EscposPreview`, not `Preview`).
- `#[derive(Widget)]` on `<Name>` generates `<Name>Ref` and
  `<Name>WidgetRefExt` (`ui.<snake_name>(cx, ids!(…))`); consumers import
  the trait.
- Window title at runtime: `ui.window(cx, ids!(main_window)).set_title(cx, …)`.
- Android packaging compiles the library as the cdylib, so `lib.rs` includes
  `main.rs` under `cfg(target_os = "android")` (see `templates/app/src/lib.rs`).

## Consuming Wadhu from another workspace

Wadhu crates name Makepad by registry version (`makepad-widgets = "2.0.0"`)
and Wadhu's root `[patch.crates-io]` resolves it to `vendor/makepad`. A
consumer, e.g. a Kumkaj app, adds the crate **and** the same one-line
patch pointing at **its own** Makepad tree:

```toml
# kumkaj-workspace/apps/<app>/Cargo.toml
[dependencies]
wadhu-escpos = { path = "../../../../Wadhu/wadhu-workspace/crates/escpos" }

# kumkaj-workspace/Cargo.toml
[patch.crates-io]
makepad-widgets = { path = "vendor/makepad/widgets" }
```

Cargo then builds **one** Makepad (the consumer's), shared by the app and
the Wadhu crate. This was verified on 2026-11-08 with a scratch consumer
that used Kumkaj's vendor tree and a Kumkaj-style raw path dependency.
Without the patch line, resolution fails (`failed to select a version for
the requirement makepad-widgets = "^2.0.0"`), because crates.io only has
`makepad-widgets` up to 1.0.0. Plain-Rust crates need no patch.

Once Wadhu has a git remote, swap the path for
`{ git = "<wadhu repo>", tag = "wadhu-escpos-v0.1.0" }`; the patch line
stays the same. Publishing Makepad-based crates to crates.io must wait
until Makepad 2 is on crates.io; plain crates can be published any time
([`CRATES.md`](CRATES.md) § Publishing).

## Look at the screen (UI work is not done until seen)

Never run test UIs on your desktop session (`:0` / Wayland). Use a
**private Xvfb** on a free display number, and never reuse a display
another session left running:

```bash
N=140; while [[ -e /tmp/.X11-unix/X$N || -e /tmp/.X$N-lock ]]; do N=$((N+1)); done
Xvfb :$N -screen 0 800x600x24 -nolisten tcp & XPID=$!
env -u WAYLAND_DISPLAY DISPLAY=:$N target/debug/wadhu-template-app & APID=$!
sleep 6; DISPLAY=:$N import -window root /tmp/shot.png      # xdotool to click
kill $APID $XPID
```

## Lockfile and MSRV

`resolver = "3"` resolves dependencies MSRV-aware: the lockfile prefers
versions compatible with the **lowest** `rust-version` declared by any
member (the template crate declares 1.85). Raise a crate's
`rust-version` deliberately; it can change the versions everyone locks.

## Packaging

Each app owns its packagers under `apps/<app>/scripts/` (copied from
`templates/app` by `scripts/new-app.sh`):

| Script | Output |
|---|---|
| `package-linux.sh` / `package-linux-dev.sh` | `dist/<app>-linux[-dev]/` |
| `windows-prod.sh` / `windows-dev.sh` | `dist/<app>-windows[-dev]/` |
| `msi.sh` `[prod\|dev]` | `dist/<MsiName>[Dev]-<ver>.msi` |
| `package-android.sh` | `dist/<app>-android/` (APK + AAB) |
| `android-dev.sh` | build + install + launch on a device |

Root helpers name **no** app — the caller sets `WADHU_APP_DIR` (and related
ids) first: `windows-env.sh`, `android-env.sh`, `stage-desktop-package.sh`,
`build-msi.sh`, `apply-android-activity-bridge.sh`, `fetch-ui-fonts.sh`,
`package-apple-scaffold.sh`. Cargo aliases:
`cargo <app>-dev`, `cargo <app>-android-dev`, `cargo <app>-windows-dev`.

MSI upgrade codes are generated per app by `new-app.sh`. **Never change
them after the first release** of that app (upgrades find the install by
those GUIDs). The `[profile.android-dev]` profile is already in
`Cargo.toml`. Isolated screenshot smoke:
`./scripts/run-ui-smoke-isolated.sh apps/<app>` (private Xvfb, never `:0`).
